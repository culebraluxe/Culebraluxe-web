# WO-410 Report

## Summary

The two functions clippy counted as having too many arguments in `db/src/forge_control.rs` — `save_learn_scan_progress`
and `file_learn_finding`, each 9/7 — now take a parameter struct. Both are the durable learn loop's write path, and in
both the positional call was the whole hazard: six of `save_learn_scan_progress`'s eight arguments interchange at the
type level (`&[String]` against `&[String]`, `&Value` against `&Value`), and four of `file_learn_finding`'s are `&str`s
in a row of which three are free text. A caller could hand the *guard* where the value belongs, or the notes where the
goal belongs, and compile. Named fields make the call site say which is which. The statements and the order they bind
are unchanged, so nothing about the schema interaction moves.

`eeeb00b0c` (the WO-406 documentation commit, the head this work started from).

WO-409's report attributes the two `forge_control.rs` sites to "WO-405 and WO-410". This commit changes both, so if

## Changes Made

### 1. Two input structs, borrowed

`LearnScanProgress<'a>` (the eight values the progress statement reads and writes) and `NewLearnFinding<'a>` (the seven
values a finding is filed from). Both borrow, like `NewForgeHold<'a>` and `CompletionUnit<'a>` in `forge_engine.rs`:
nothing in them outlives the statement that binds it, so no call site pays an allocation to name a field.

The field names carry the distinction the positional call could not. In `LearnScanProgress` the `expected_*` half is the
statement's guard and the plain half is what it writes — the retry rule ("`Ok(false)` means someone else moved the row,
retry the chunk on the next pass") only means anything if a reader can tell which is which. In `NewLearnFinding`,
`ready` is a branch rather than a value: `true` files the story `Ready` and stamps exactly one work item, `false` stages
it in the learning batch.

### 2. Signatures and bodies

Both methods take one borrowed struct, and their statements bind `progress.…` / `finding.…` where they bound a bare
name. Two inline format captures had to become explicit arguments — the `forge-learn-finding:{repository_key}:{finding_key}`
key and the `stored_key` built from it now pass `finding.repository_key` / `finding.finding_key` — because an inline
capture names a local and the locals are gone.

### 3. The sixteen call sites

| file | sites |
| --- | --- |
| `tests/src/forge.rs` | 14, all in `mod learn_durable_tests` |
| `forge/src/engine/learn.rs` | 2 (`file_candidate`, `save_progress`) |

Four of the fourteen test sites build the future and await it *later* (`let writer_a = dao.save_learn_scan_progress(…)`
then `tokio::join!(writer_a, writer_b)`, and the same shape once for `file_learn_finding`). There the input struct must
be a named local: a temporary dropped at the end of the `let` statement leaves the future borrowing freed memory
(`E0716`), which the compiler caught at all four sites. They now hoist the struct into `progress_a`/`progress_b` and
`finding_a`/`finding_b` and pass a reference. Where the call awaits in the same statement, the struct literal stays
inline.

### 4. Re-exports

`db/src/lib.rs` re-exports both structs beside the DAO that takes them.

## Close-out: the four residue sites are done (2026-10-13)

The section above named the four remaining `too_many_arguments` findings and recorded one reason they could not be
fixed: "the two `signer.rs` ones cannot be fixed inside `db`: the `web` crate's `SignerDao` trait mirrors their argument
lists, so the struct has to be threaded through that trait". That reading was wrong, and this close-out is the
correction: the trait is `web`'s PORT, and WO-409 already set the precedent for ports (`open_hold`'s struct landed
while the forge-side `OpenHold` port kept its shape). Only the trait's *implementation bodies* call the DAO, so the two
`web` wrappers build the struct and hand it over while the trait's own signatures stay exactly as they were.

Four input structs, all borrowed, one per site — the same move WO-409 and WO-410 made, on the Luxesign (forms and
signature) surfaces rather than the learn loop:

| function | args | struct introduced | call sites updated |
| --- | --- | --- | --- |
| `AppErrorDao::record_application_event` | 8/7 | `NewApplicationEvent<'a>` (`db/src/app_error.rs`) | 1: `web/src/api/error_capture.rs` |
| `resolve_for_issuance` | 8/7 | `SignatureIssuance<'a>` (`db/src/broker_signature.rs`) | 1: `db/src/vault/bind_form_to_contract.rs` |
| `SignerDao::accept_consent_tx` | 8/7 | `NewRecipientConsent<'a>` (`db/src/signer.rs`) | 1 body: `web/src/signer/mod.rs` |
| `SignerDao::append_evidence_tx` | 9/7 | `NewEvidenceEvent<'a>` (`db/src/signer.rs`) | 1 body: `web/src/signer/mod.rs` |

Why these four are worth naming rather than tolerating, in the terms each site's own hazard:

- **`record_application_event`** binds `route` and `meta` one after the other, both caller-supplied `&str`s; the table's
  own comment says the page that failed (`route`) and the taxonomy that has no column (`meta`) are the two that matter.
- **`resolve_for_issuance`**'s tail three (`authority`, `issued_at`, `require_execution_slot`) are the BRANCH — issuance
  against preview — and eight positional arguments made that trio read as three more inputs.
- **`accept_consent_tx`** binds `consent_version` and `consent_text_sha256` next to each other and casts neither, so a
  transposition writes a consent row holding a version the recipient never accepted.
- **`append_evidence_tx`** binds four optional ids in a row (`recipient_id`, `actor_id`, `correlation_id`,
  `causation_id`) of which only the first is a `uuid` cast, so swapping the actor for the correlation id compiles and
  writes a trail naming the wrong party.

Statement text, bind order, `DbFailure` labels and the uuid casts are byte-identical; this is a Rust signature change
with no migration and no behaviour change. One message construction moved from an inline named argument to a positional
one (`format!("... for {template_id}.")` to `"..."` plus the `issuance.template_id` argument) and produces the same
string.
