## 1. The bug at HEAD

`DbReleaseEvidenceStore::merge` (`forge/src/engine/git_publish.rs:262-281`) ran the
`merge_workflow_evidence` write and, on failure, `eprintln!`d it and returned `()` — the
`EvidenceStore::merge` signature (`forge/src/engine/release.rs:67`) is `()` by trait, so
there was nowhere to put the error. Downstream, `release.rs::publish()` (line ~253) merges
the `{publish_succeeded: true, published_sha}` patch and unconditionally returns
`Success("published {sha}")`. A push that landed while the write failed therefore read as a
clean publish with nothing recorded — every later step acted on stale evidence.

## 2. Changes (only `forge/src/engine/git_publish.rs`; no other file)

- New `UnrecordedPublish { story_id, published_sha, failed_release_stage, error }`
  (pub(crate)): a refused merge, captured — `published_sha` is `Some` exactly when the push
  had landed.
- `DbReleaseEvidenceStore` (was a unit struct) now carries an
  `Arc<Mutex<Option<UnrecordedPublish>>>` slot with `take_unrecorded()`. `merge` captures
  the failure into the slot instead of logging it. No `eprintln!` remains on this path: the
  error is returned, not logged.
- New `unrecorded_publish_hold(command_id, &unrecorded) -> ApplicationCommandResult`:
  `Conflict` (never Success) with `HOLD: published {sha} but …` when the push had landed,
  else `HOLD: the release evidence write failed … at stage …` — the SHA is in the reason.
- `HostReleaseExecutor::execute` builds a fresh store per command, runs the inner executor,
  then returns the hold when the slot is set. The store is constructed nowhere else
  (verified by grep), so every production merge flows through the check and no silent path
  remains. When the database is healthy the slot stays empty and the result is byte-identical
  to before.
- Deliberately NOT added: a new `PublishOutcome` variant. `release.rs::publish()` ends in
  `_ => unreachable!()` and is outside Owns — a variant nobody there handles would panic
  production. The hold travels in the command result, which this file owns end to end.
- `read()` failure (`unwrap_or_else` + `eprintln!`, line ~256) untouched: a read is not the
  write this order covers, and default-evidence on read failure is load-bearing for fresh stories.
