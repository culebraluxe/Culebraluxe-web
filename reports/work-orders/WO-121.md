## §3 — the worktree guarantee

The gap was not a missing `remove` call. It was a missing **owner**. Four sites each decided cleanup
inline, and one authority — `handles…join().expect("lane worker wrapper contains panics")` — could
panic out of `execute_durable_batch`, taking every worktree in the batch with it under a panic that
named none of them.

`LaneWorktree` is now that owner. It is created the moment `provision_worker_workspace` returns and it
lives until the drive loop has settled the lane. It carries one disposition, decided once:

- **release** — remove the tree, and the branch with it only while the branch still sits at its base. A
  branch that moved holds a candidate, so it stays, and the line names it.
- **retain** — keep the tree and say where it is and which branch it holds.
- **`Drop`** — the backstop for the exit nobody wrote. A lane that exits before handing the tree over
  (an early return, a panic) still gets a disposition and a line:
  `forge-wave worktree_disposition=retained_on_exit worktree=… branch=…`.

The backstop **retains rather than deletes**, and that is a deliberate reading of this repository's
doctrine rather than an oversight: a lane that failed may hold work no branch has, and `MEMORY.md`
("PAID CODE > GIT SHA") puts the code first. A panic is not evidence that a worktree is empty. What the
guard guarantees is that the tree is never *unrecorded* — and that no panic can carry the batch away:
the join failure is now a recorded per-lane failure with its claim settled (`lane_that_never_reported`).

## Tests

Seven new tests in `drive.rs`'s `concurrency_tests` module (4 pre-existing, 11 total), each pinning one
of the facts above:

- `a_secondary_failure_is_reported_beside_the_primary_one`
- `a_panicking_lane_is_a_recorded_failure_and_keeps_its_sibling_result`
- `a_panicking_lane_reports_the_claim_it_could_not_settle`
- `a_lane_that_never_reports_names_the_panic_and_settles_its_claim`
- `a_release_that_fails_is_returned_and_attempted_only_once`
- `an_undecided_lane_worktree_is_retained_by_its_drop_not_deleted`
- `a_released_lane_worktree_is_removed_once_and_a_retained_one_is_not_removed`

Two new doubles: `PanicRunner` (a lane that panics instead of reporting) and `RefusingFailJobs` (a
claim that cannot be settled — the second failure this work order is about).

**Honest note on "pre-fix red":** these are contract tests, not reproductions. A swallowed error has no
failing assertion to write pre-fix — the pre-fix evidence is the quoted `let _ =` sites in the table
above, and the observable difference post-fix (the populating of `settlement_failure`, and a
disposition that can be read). The panic path is the exception: pre-fix, a runner panic inside the lane
wrapper produced an `Err(_)` whose only trace was a log line, and the settle that failed was erased;
both are asserted now.

Test doubles never shell out to git: the guard takes its remover as a function
(`LaneWorktree::with_remover`), which is what makes the disposition assertions real and cheap.

## Judgment calls, for the captain

1. **Error identity is never traded for a message.** Where a failure crossed a boundary owned by another
   module (S2, S4), the original error is returned unchanged — its `code()` is how
   `is_engine_fault_error` and the retry policy classify it, and a prettier message is not worth an
   unknown classification. The second failure is reported beside it instead.
2. **Three "cleaned and logged" paths now also hold the story** (S7, S8, success tail) when nothing else
   held it. A tree Forge could not remove is a fact an operator has to be able to see without reading a
   log; holding keeps the file's existing convention for settlement failures. If that is too loud for a
   cleanup problem, it is a one-line change at each site — the guard reports either way.
3. **Retain on failure, release on success and `TASK_ALREADY_COMPLETED`.** The work order's diagram reads
   "success OR error OR panic → cleanup/release"; this implementation releases where the tree's work is
   already accounted for and retains where it may not be, and always names the branch. Nothing is
   deleted that a branch still holds, and nothing is left unnamed.
4. **The base commit and the branch name travel with the guard**, so the release decision can tell a
   branch that never moved (safe to delete) from one that holds a candidate (must stay).
