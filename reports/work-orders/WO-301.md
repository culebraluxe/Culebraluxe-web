# WO-301 Report

## Summary
Fixed the durability bug where a transient final-heartbeat failure after a paid turn execution could cause the same turn to be re-executed. Also made poison-sensitive lock sites in the heartbeat supervisor poison-tolerant.

## Pre-fix SHA
`6852fc081606c49d830bbc0afc8f22be86348e64`

## Changes Made

### 1. Final-heartbeat failure path in `forge/src/engine/executor/drive.rs`

**Symbols corrected:**
- `drive_forge_story_inner` (non-parallel path, lines ~1169)
- `drive_forge_story_inner` (parallel path, lines ~1202)

**Old behavior:** `durable.jobs.complete(&lease.job_id, opts.worker_id)?` propagated the error with `?`, causing the drive to return an error. On the next pass, the Workflow task would still be READY (since the completion write failed), causing the turn to be re-executed and paid for again.

**New behavior:** When `durable.jobs.complete` fails:
- Log the error with a "preserving paid turn for reconciliation" message
- Continue without propagating the error
- The Workflow task remains in a state requiring reconciliation
- A later Forge pass will reconcile the durable state without re-executing the turn

**Handling chosen:** Record and continue (WO-301 pattern B/C) — the paid turn fact is preserved, persistence failure is recorded, reconciliation is enabled.

### 2. Poison-tolerant locks in `forge/src/engine/job.rs`

**Symbols corrected:**
- `heartbeat_state.consecutive_db_failures.lock()` at two sites in the heartbeat supervisor (lines 434, 438)

**Old behavior:** `.lock().unwrap()` would panic if the mutex was poisoned, crashing the heartbeat supervisor and losing lease authority.

**New behavior:** `.lock().unwrap_or_else(|poisoned| poisoned.into_inner())` recovers the inner value from a poisoned mutex, allowing the heartbeat supervisor to continue operating.

**Handling chosen:** Propagate with recovery — poison is handled locally without panicking the durability path.

**Symbols corrected (error-loss sites):**

- `jobs.fail` calls (2 sites in `execute_durable_batch`)
- `remove_lane_worktree` call (1 site in TASK_ALREADY_COMPLETED handling)

**Old behavior:** Silent error discarding with `let _ =` or `.ok()`

**New behavior:** Errors are logged via `eprintln!` but propagation continues correctly

**Handling chosen:** Record and continue for cleanup errors; proper filtering for env vars.

## Residual Risk

1. **Worktree cleanup on panic**: The `execute_durable_batch` uses `catch_unwind` and returns results for all lanes including panicked ones. The main loop cleans up worktrees for successful completions (line 948-955) but retains worktrees for engine faults (line 805-809 logs "isolated worktree retained"). This is intentional for debugging but could leave orphaned worktrees on repeated engine faults.

2. **Reconciliation automation**: The fix preserves the paid turn for reconciliation, but the actual reconciliation pass (a later Forge run) must be triggered manually or by the scheduler. No automated reconciliation trigger was added.

3. **TASK_ALREADY_COMPLETED handling**: In the non-parallel path, when `TASK_ALREADY_COMPLETED` is returned, we now log and continue instead of propagating. This is correct because the Workflow task is already complete, but the durable job needs settlement. The settlement failure is logged for reconciliation.

## Rebase onto the landed WO-121

**Why a rebuild was needed.** This branch originally started from
`6852fc081606c49d830bbc0afc8f22be86348e64`. That commit is the parent of WO-121 as well as of
WO-301, so the original branch did not contain WO-121, and WO-121 was landed on `main` first as
`e33d40b424ce781fb1d59a5bf19df84dbb11c6f2`. For the rebased branch the pre-fix state is therefore
the landed WO-121, not `6852fc081606c49d830bbc0afc8f22be86348e64`.

**How it was rebuilt.** `git rebase --onto e33d40b424ce781fb1d59a5bf19df84dbb11c6f2 6852fc081606c49d830bbc0afc8f22be86348e64`,
run in a separate worktree so the published `wo/301` was left untouched.

**What the overlap was.** The rebase produced ten conflict blocks, all in
`forge/src/engine/executor/drive.rs`, and all of the same kind: this branch had replaced
`let _ = ...` and `.ok()` at sites that WO-121 rewrote as named failures with explicit lane
dispositions. Every conflict was resolved by keeping WO-121's implementation, because WO-121 owns
those sites and its version carries the failure into the run outcome. The duplicated lines this
branch had added at those sites are gone, which is why the difference from the landed base is now
thirty-six added lines and nine removed lines in that file, rather than the hundred and twenty-one
added and twenty-seven removed of the original commit.

**What this branch changes relative to the landed WO-121, stated exactly.**

1. `forge/src/engine/executor/drive.rs`, four environment-variable readers
   (`GENERATION_TURN_CAP_ENV`, `WITHIN_STORY_CONCURRENCY_ENV`, and `TURN_CEILING_ENV` at two call
   sites): an empty string is filtered out, so an empty variable means "not set" rather than
   "set to nothing".
2. `forge/src/engine/executor/drive.rs`, three durable settlement sites in the non-parallel path:
   `jobs.complete` after `TASK_ALREADY_COMPLETED` no longer propagates with `?`; `jobs.fail` in
   the same branch no longer propagates with `?` (the original error is still returned); and the
   final `jobs.complete` no longer propagates with `?`. In each case the settlement failure is
   written to the error stream with a "preserving paid turn for reconciliation" message and the
   run continues, so a turn that has already been paid for is not executed a second time merely
   because its settlement write failed.
3. `forge/src/engine/job.rs`, two lock sites in the heartbeat supervisor: `.lock().unwrap()`
   became `.lock().unwrap_or_else(|poisoned| poisoned.into_inner())`, so a poisoned mutex no
   longer panics the heartbeat supervisor and loses lease authority.

**A difference worth naming rather than hiding.** WO-121 handles this class of failure in the
parallel path by setting a `hold_reason`, which holds the story and names the failure in the run
outcome. `hold_reason` is declared at line 1045 and consumed at line 1228; the non-parallel path
begins after that, so it is not in scope at the three settlement sites above. This branch
therefore writes to the error stream only, which is weaker than WO-121's standard of naming every
failure in the outcome. Closing that gap means either a new hold path for the non-parallel path,
or attaching a secondary failure to the returned error at the `jobs.fail` site. Both are new
behaviour and belong to a work order that asks for them, not to this rebase.

**Verification after the rebase.** `cargo test -p forge`: 582 passed; 0 failed; 2 ignored.
`cargo clippy -p forge --all-targets`: 60 warnings (33 duplicates), no errors — the same count as
the landed WO-121 base. WO-121's machinery is intact by count: `with_secondary_failure` six
occurrences, `settlement_failure` eleven, `fail_claimed_lane` six, each unchanged from
`e33d40b424ce781fb1d59a5bf19df84dbb11c6f2`.

**A formatting correction applied to this branch.** The two settlement statements rewritten in
`forge/src/engine/executor/drive.rs` were 112 characters wide, so rustfmt required them wrapped,
and the `rust format` step in `gates.yml` counted them as new unformatted hunks in a file that was
canonically formatted at the base. They are now wrapped as rustfmt requires. The change is
whitespace only and no behaviour changed. The `git diff --check → clean` line in the Verification
block above cannot catch this, because that command looks for trailing whitespace and conflict
markers, not formatting. Separately: that same step was already failing before this work, for 42
unformatted hunks across the tree (`cli/src/forge/repo_guards.rs`, `forge/src/engine/db_ledger.rs`,
`maestro.rs`, `opencode.rs`, `roles/*`, `tests/tests/*`). That debt is pre-existing and is not
addressed here.
