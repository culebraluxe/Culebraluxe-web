## 0. Architecture that is already in force

```text
Storyboard / agent_work_item
        │ story scheduling
        ▼
Workflow Engine + FORGE_SDLC-v6.xml
        │ READY workflow role task
        ▼
ForgeJobBridge
        ▼
JobService
        │ lease / heartbeat / attempts / backoff / recovery / cancel
        ▼
ForgeServiceRegistry
        ▼
AbstractForgeService
        │ inherited shared lifecycle
        ▼
Concrete Forge role service + ForgeRoleHooks
        ▼
OpenCodeHarness
        ▼
model/runtime
```

Ownership is settled:

- **Workflow/XML** owns state, sequencing, routing, human gates and service binding.
- **JobService** owns durable role-execution reliability and must remain role-agnostic.
- **Concrete Forge services** own role intelligence/interpretation.
- **OpenCodeHarness** owns model/process/session/runtime mechanics.
- **DEV_OPS** owns release/publish authority; Inspector/Assay do not mutate Git.
- `agent_work_item` is the story-level dispatch queue; `jobs(type='forge.role')` is the role-job queue. They are separate by design.
- `forge_work_queue` (269; wired as an **inlet** by 270) is a batch inlet, not a third queue: a `Pending` row owns admission and pacing only, and the one thing it does is hand its story up — the story's `Ready` transition, made through `forge_dispatch_story`, the board's own ENGINE RUN Q verb. Nothing downstream knows the row existed: the item is the trigger's (025/146/259), the run is the engine's (264), the lanes are the worker's. Both steps live in `forge_reconcile_dispatch_queue()` (settle, then arm, wrapped around 265's three repairs), which the worker already calls once per pass — so this is SQL only, and it runs where the worker runs: PROD. `forge_work_queue_config.arm_limit` (default 3) is the whole rate control: how many door rows may be in flight at once, i.e. how many runs a batch opens concurrently. `harness`/`execution_target` are provenance, not routing — the claim (262) has no target filter, the worker resolves its harness from its own environment, and `ran_as` is stamped at settle from the run's own `model_used`, so declared intent and observed fact are two columns with one writer each. A story `Failed` is terminal at the door: the engine owns repair inside a run, and the queue must not spend further turns on a story Forge has given up on.

## 2. ACTIVE WORK — one remaining implementation lane

### Lane A — DeepSeek: JobService reliability closure

**Owns only:**

```text
forge/src/engine/job.rs
forge/src/engine/executor.rs
forge/src/engine/engine_fault.rs       only if required
rust/test-harness/tests/forge_job__*.rs
```

Do not redesign Workflow, role services, OpenCode V2 or service binding.

#### A1 — classify transient infrastructure failures correctly

Measured gap: generic JobService supports retryable failure (`permanent=false`), but the Forge role execution path currently terminalizes service errors as permanent.

Required rule:

```text
typed infrastructure unavailable / connection failure
    → JobService.fail(... permanent=false)
    → bounded backoff/retry

actual role/business/configuration verdict
    → JobService.fail(... permanent=true)
```

No string matching on error text. Use the narrowest existing typed classification (`WorkflowError::Unavailable`, connection/engine-fault helpers as appropriate).

Rails must prove retry/backoff/max-attempt behavior and that the Job layer remains role-agnostic.

#### A2 — review Workflow-completion failure settlement

After a role succeeds, `complete_role_task(...)` can fail. A temporary persistence/transport failure must not automatically become a permanent story verdict, but the paid role turn also must not be dispatched twice.

Preserve the invariant:

```text
Workflow completion/state wins before the durable job is marked Completed.
```

Make only the narrowest recovery/classification change supported by the existing state model, with a regression test for the crash/failure window.

#### A3 — prove or add a real execution deadline

Lease expiry is not automatically a maximum runtime because a healthy worker can continue heartbeating.

First prove whether a separate wall-clock execution deadline already exists. If it does, pin it with a test. If it does not and the architecture requires one, add the smallest **generic, configurable, observable** JobService/worker deadline. Do not put model- or role-specific policy into JobService.
