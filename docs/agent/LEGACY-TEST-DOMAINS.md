# Legacy tests by domain — what the 465 files are about

Generated by `python3 scripts/legacy-test-domain-map.py --write` from the legacy files
themselves. `docs/agent/legacy-test-parity/domains.tsv` is the per-file table; this page is
the same data as a map. The conversion ledger (`docs/agent/LEGACY-TEST-PARITY.md`) answers
*how far along* each file is; this answers *what pile it belongs to*, which is the question
to sort by when the queue is worked area by area.

## How a file gets its area

1. Every import votes for the area its module is part of, a rarely-imported module voting
   louder (`1 / files that import it`). `db/query-executor` is the fake transaction runner in
   75 files; it votes, but it cannot decide a file on its own.
2. The harness never votes: `db/query-executor`, `db/tx`, `lib/portal-write-error`, `fake-sql`,
   `harness`, `test-support/`, `scripts/`, fixtures. These are how a test is wired, not what it
   is about.
3. A weak vote (under 0.2, i.e. one common module) loses to the file's own name, because
   `forge-story-batch-deploy.test.ts` imports `sql` from `db/client` simply to run SQL.
4. A file with no imports at all is classified from its path.

An area is a *location in the product*, not a claim about coverage. A file in `core/forms`
is a file about forms; nothing here says whether Rust pins it yet — that is column one of the
ledger, and the two are joined in the queue table below.

## Regenerating and re-labelling

```sh
python3 scripts/legacy-test-domain-map.py            # the counts, on stdout
python3 scripts/legacy-test-domain-map.py --write    # + domains.tsv and this page
```

The script is the single writer of both artifacts: a file's area is corrected by editing
`AREA_RULES` in the script (one rule per area, first match wins), never by editing the TSV —
a hand-edited row would be overwritten on the next run and would give one fact two authors.
